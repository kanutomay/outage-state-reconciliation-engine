# Known Limitations & Security Boundaries

This is a scannable summary of what this system does and doesn't guarantee today, and what's next. It intentionally stays current-state and forward-looking - the detailed round-by-round "an earlier version did X, here's why it broke" narrative, and the planned-fix code sketches, live in [docs/audit-history.md](audit-history.md) rather than here, so this stays a reference instead of a transcript.

## Current limitations

**L1 - CLEANUP is internal-only by construction, not by convention.** The public entry Lambda ([`src/ingestion/entry_handler.py`](../src/ingestion/entry_handler.py)) only accepts `CREATE`, `UPDATE`, `CLOSE` and hard-rejects anything else with `400`. CLEANUP messages are produced exclusively by [`src/maintenance/ticket_cleanup_handler.py`](../src/maintenance/ticket_cleanup_handler.py), which has its own IAM-authorized `sqs:SendMessage` permission on the shared lifecycle queue - that Lambda contains no HTTP/API-key code path at all, so there's no way to submit CLEANUP externally, with or without a valid key.

**L2 - Category is limited to `HFC Access` and `FTTH Access`.** The system was built specifically for a Fixed broadband line of business; the customer-impact table only has HFC/FTTH node inventory, and the FTTH subscriber-impact lookup is hardcoded to that category. Expanding to Voice/Video/Mobile would require extending the node inventory and making the impact-lookup logic configurable per category.

**L3 - CLOSE is not fully idempotent by policy choice.** Pre-queue validation can be configured to reject a CLOSE against an already-closed ticket with `409`, specifically so operators get visibility into upstream systems that aren't syncing ticket state correctly. `CLOSE_IDEMPOTENT=true` (the default) instead treats it as success.

**L4 - UPDATE replaces the entire node list, not a delta.** There's no "add this one node" / "remove that one node" call - the caller sends the complete current node list and the processor diffs it against what's stored to determine ADDED/REMOVED. Simpler to implement, but a caller with stale local state can accidentally drop nodes it didn't intend to remove.

**L5 - The SLA threshold is a Lambda environment variable, not a runtime setting.** Changing the 72-hour default requires a CloudFormation parameter update and redeploy - there's no central config store yet, so different markets can't run different thresholds without separate Lambda deployments.

**L6 - Node-conflict validation is read-then-decide, not atomic.** `check_nodes_have_open_tickets()` in [`prequeue_validation.py`](../src/validation/prequeue_validation.py) queries DynamoDB, sees no conflict, and *then* the request is allowed onto the queue - there's a real window where a second, concurrent CREATE for a *different* ticket ID targeting an overlapping node can pass the same check. SQS FIFO ordering doesn't close this: messages are grouped by `MessageGroupId=ticket_id`, so two different ticket IDs are never serialized against each other. The correctness guarantee has to live in the downstream ticket-processor Lambda (not included here), as a conditional write at the point nodes are actually attached to a ticket - see [docs/audit-history.md](audit-history.md) for the full reasoning. Treat this validation layer as a fast, good-UX early rejection for the common case, not the system's sole uniqueness guarantee.

**L7 - Validation fails closed on backend errors, by design.** If DynamoDB can't be reached at all - or even one lookup fails in an otherwise-successful batch - `run_prequeue_validation()` returns `503 VALIDATION_SERVICE_UNAVAILABLE` and blocks the request, overriding shadow mode. For outage-tracking state specifically, a false "accepted" is worse than a retryable rejection - see [Security boundaries](#security-boundaries) and [docs/audit-history.md](audit-history.md) for why this was a deliberate tradeoff.

**L8 - Ticket-uniqueness detection is a bounded, paginated table scan, not an indexed lookup.** `check_ticket_exists()`'s ticket-ID-scoped fallback follows `NextToken` across pages, bounded by `MAX_TICKET_LOOKUP_PAGES` (5 pages, ~1,000 items) so the entry Lambda's 23-second timeout can't be exhausted by an unbounded scan. That's a considerable improvement over an unpaginated single call, but it's still a bound, not a guarantee: a table with more than ~1,000 items ahead of a ticket's rows in scan order could still miss a genuine match. The real fix - a Global Secondary Index on `Ticket_Number`, turning this into an indexed point lookup with no page limit at all - is tracked under [Planned improvements](#planned-improvements).

**L9 - `OpCo` scopes conflict/duplicate checks, but nothing verifies the caller is entitled to claim it.** Every DynamoDB lookup in `prequeue_validation.py` filters on the table's `opco` attribute, and `entry_handler.py` passes the request body's `OpCo` field through end to end - so a ticket ID or node ID reused across two operating companies sharing this table is never treated as a collision between them. What this does *not* do is authenticate the value: `OpCo` is read straight from the request body and trusted as-is. In this illustrative implementation, `OpCo` scopes data lookups but is not an authorization credential - it's a *data-scoping* field, not an *access-control* one. A production deployment should derive the authorized OpCo from the authenticated principal (an API-key mapping, a JWT claim, or equivalent) and reject any conflicting caller-supplied value, rather than trusting it as-is; that logic conceptually belongs in the API-key/routing Lambda in front of this repo's entry Lambda (see [architecture-overview.md](architecture-overview.md)), not in the code sampled here.

**L10 - A CREATE that returns `200` can be immediately followed by an UPDATE or CLOSE that 404s.** `entry_handler.py` enqueues a CREATE message and returns success as soon as the SQS send succeeds - the actual DynamoDB item is written later, by the downstream processor Lambda (not included in this repo), when it dequeues that message. `validate_update_request()`/`validate_close_request()` do a synchronous, strongly-consistent existence check at request time, so a client that CREATEs a ticket and immediately UPDATEs or CLOSEs it can have that second check run before the write lands. The shared queue's ordering guarantee (see [Major resolved issues](#major-resolved-issues)) is unaffected by this - it's correct once messages are enqueued; the gap is entirely upstream of the queue. The `404 TICKET_NOT_FOUND` response includes a `blocked_reason.note` telling the caller the ticket may still be in flight and to retry shortly, rather than reading as "this ticket ID is wrong." See [docs/audit-history.md](audit-history.md) for the four approaches weighed and the planned reservation-record fix.

**L11 - A retried request that collides with SQS FIFO's content-based dedup gets a `200` whose `correlation_id` never appears downstream.** The dedup hash deliberately excludes `correlation_id` (a genuine retry can carry a different trace ID, and including it would defeat dedup entirely), so a request that collides with an in-flight duplicate still gets its own fresh `correlation_id` in its synchronous response - but only the *original* message's ID ever reaches the processor, DB-write, and notification Lambdas. SQS's `SendMessage` API doesn't report back whether a send was deduplicated, so the entry Lambda has no way to detect this at send time. See [Planned improvements](#planned-improvements) for the idempotency-cache fix that would close this.

## Security boundaries

- **Fail-closed validation.** A DynamoDB outage - total or partial - blocks the request with `503` rather than letting it through unverified (L7).
- **Parameterized queries, no injection surface.** Every DynamoDB lookup uses parameterized PartiQL or key-condition queries; `ticket_id`/`node_id` values are validated against a strict allowlist pattern (`_SAFE_ID_PATTERN`) before touching any query, and are never string-interpolated into a statement.
- **Transport security.** Every SQS queue in this stack - the lifecycle queue and both dead-letter queues - denies any non-TLS access via an explicit queue policy.
- **`OpCo` is a data-scoping field, not an access-control one** (L9) - it isolates one tenant's conflict checks from another's on a shared table, but doesn't by itself stop a caller from claiming a tenant it doesn't belong to. Closing that requires an authorization layer, outside this repo's flagship samples, that derives the caller's permitted OpCo(s) from their authenticated identity.
- **Data handling & logging scope.** Structured logs retain correlation IDs and the minimum ticket/node identifiers needed to confirm delivery and diagnose processing failures. Full request payloads, subscriber data, authentication material, and detailed topology attributes are excluded. A validation-conflict response to an authenticated caller may include the specific conflicting node/ticket IDs - functional data a legitimate client needs to remediate its own request - which is treated differently from what's pushed into a log group or an SNS notification; exception text going to either is truncated to a fixed length rather than passed through raw.

## Major resolved issues

- **Ticket-lookup false negatives on UPDATE/CLOSE** - exact string matching on ticket ID missed IDs with incidental whitespace/formatting drift from the upstream system. Switched to a parameterized PartiQL `begins_with()` query.
- **Over-strict validation on UPDATE/CLOSE** - category/impact rules were applied to every intent, incorrectly rejecting CLOSE requests when those fields had legitimately changed since CREATE. Now validated only on CREATE - the origin of this codebase's "validate on creation, trust on closure" principle.
- **PartiQL injection and a response-shape bug in the fallback ticket lookup** (security review) - the fallback path interpolated `ticket_id` directly into a PartiQL statement and returned raw DynamoDB attribute-value wrappers instead of parsed values. Fixed with parameterized queries, strict identifier validation, and consistent parsing via `parse_dynamodb_item()`.
- **SQS deduplication didn't actually deduplicate retries** (security review) - `MessageDeduplicationId` was a random UUID per send, so a genuine retry never collapsed with the original. Replaced with a stable content hash of the request.
- **Separate per-intent queues never actually guaranteed lifecycle ordering** (release review) - FIFO only orders within one queue and message group, so a fast UPDATE/CLOSE could reach the processor before its own CREATE. Collapsed onto a single shared `LifecycleTicketQueue` grouped by `MessageGroupId=ticket_id`.
- **Duplicate tickets could evade the CREATE existence check by naming different nodes** (release review) - the per-node lookup alone wasn't enough, since node lists drift over a ticket's life (L4). Added a ticket-ID-scoped fallback scan (see L8 for its bound).
- **Partial DynamoDB failures were silently treated as fail-open** (release review) - only a *total* lookup failure raised an error; any single failed lookup in a batch now fails the whole check closed.
- **A CREATE with no nodes bypassed duplicate/conflict validation entirely** (correctness review) - a bypass guard skipped validation outright when `nodes` was empty. Removed; `Devices` is now enforced as required for CREATE at the API layer too.
- **`OpCo` was documented as required but never checked** (correctness review) - now enforced with a `400` on any intent missing it.
- **Malformed node IDs were silently skipped instead of rejected** (correctness review) - every node ID is now validated, and a mismatch rejects the whole request with `400`.
- **The SQS dedup hash omitted `OpCo`/`category`** (correctness review) - two genuinely different requests sharing everything else could collapse into one message. Both fields are now part of the hash.
- **`correlation_id` was only read from a case-sensitive header** (correctness review) - the documented body field was ignored. Header lookup is now case-insensitive with a body-field fallback.
- **Cleanup only read the first page of stale tickets** (correctness review) - `Limit=500` with no `NextToken` pagination silently dropped tickets past the first page. Fixed with full pagination, bounded by a safety cap.
- **The ticket-ID-scoped lookup stopped after one page** (peer review) - the same `Limit`-bounds-evaluated-not-matched gap as above, but in `check_ticket_exists()`, could report a real ticket as not found. Fixed with `NextToken` pagination (L8).
- **`OpCo` was threaded through SQS and the dedup hash but never into the DynamoDB queries that decide duplicates/conflicts** (peer review) - fixed by adding an `opco` filter to every lookup (L9).
- **Cleanup truncated any ticket ID containing an underscore** (peer review) - `Ticket_Number.split('_')[0]` broke on ticket IDs like `INC_2026_001`. Fixed to strip the known `_{node_id}` suffix instead of splitting.
- **The operations dashboard queried a log group name that didn't match the included CloudFormation** (peer review) - fixed to match the actual `-prod`-suffixed name.
- **A CloudFormation `Region` parameter could disagree with the stack's actual deployment region** (peer review) - replaced with the `AWS::Region` pseudo parameter.
- **The non-TLS-transport deny policy only covered the main lifecycle queue** (peer review) - added matching policies for both dead-letter queues.

Full narrative for each of these - what the earlier version did, why it was wrong, and the reasoning behind the fix - is in [docs/audit-history.md](audit-history.md).

## Planned improvements

- **A Global Secondary Index on `Ticket_Number`** (or a dedicated ticket-header item outside the per-node item shape) - turns the bounded/paginated ticket-uniqueness scan (L8) into an indexed point lookup with no page limit to hit. Deferred here because it requires a table/GSI change outside this repo's validation-layer scope.
- **Optimistic locking on the ticket item** (version-checked conditional writes) - would let the processor-to-DB-write invocation become asynchronous without reintroducing the write-ordering race that synchronous chaining currently prevents; the same conditional-write pattern is the eventual fix for L6, applied to node claims instead of ticket versions. See [docs/audit-history.md](audit-history.md) for the code sketch.
- **A synchronous reservation record, or an idempotency-key result cache** - the real fixes for L10 (the CREATE/UPDATE race) and L11 (the dedup/correlation-id mismatch), respectively. Both are sketched in [docs/audit-history.md](audit-history.md) but need coordination with the downstream processor's real read/write contract, which isn't part of this repo.
- **Structured logging end-to-end** - the DB-write and notification Lambdas still log with plain `print()`, which breaks CloudWatch Logs Insights queries that expect structured fields on every hop.
- **Broader automated integration coverage** - the repository now includes sanitized executable contract tests for the reconstructed entry and cleanup samples. Full multi-component integration testing still requires production components intentionally omitted from this portfolio; [tests/README.md](../tests/README.md) separates the public automated coverage from the historical internal acceptance evidence and the remaining scenario catalog.
- **Multi-region support** - the stack assumes a single region throughout; this would require parameterizing region references consistently across the Lambdas and CloudFormation.
- **Notification recipients in configuration, not code** - currently requires a Lambda redeploy to change; the fix is Parameter Store or a DynamoDB-backed distribution list.
- **Fuller dev/prod separation** - some shared resources (notably node inventory) currently span both environments.
- **Retry on the subscriber-impact lookup** - a timeout currently falls back to a default value with no retry and no explicit failure logging.
