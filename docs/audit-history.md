# Audit History & Detailed Rationale

This file holds the detailed, round-by-round narrative behind the summary in [known-limitations.md](known-limitations.md): what an earlier version of this code did, why it was wrong, and - where relevant - the planned-fix code sketches that were weighed but not implemented within this repo's scope. It's kept separate on purpose, so `known-limitations.md` stays a scannable, current-state reference rather than an audit transcript. If you want the full "why" behind a decision, it's here.

## Recovering from an undocumented handover

The system was inherited with effectively no documentation and had to be reverse-engineered from the Lambda code alone before any confident changes could be made. That experience is the reason this documentation set (architecture, API reference, observability, known limitations, this file) exists at all - undocumented "why" decisions are the most expensive kind of technical debt to pay down after the fact.

## L1 - CLEANUP structural exclusion, in detail

An earlier version of this repo had the public entry Lambda accept `intent=CLEANUP` and simply skip validation for it, on the assumption that "nobody but the schedule would send that." That assumption doesn't hold - anyone holding a valid client API key could have submitted `CLEANUP` directly. The fix removes the assumption entirely: the public entry Lambda now only accepts `CREATE`, `UPDATE`, `CLOSE` and hard-rejects anything else with `400`. Precisely: the cleanup Lambda isn't unreachable from a client request because it lacks network access - it's unreachable because it contains no HTTP/API-key code path at all, with or without a valid key, that would parse or accept a client-submitted CLEANUP request. The CLEANUP-skip branch still present in `prequeue_validation.py` is retained purely as defense-in-depth for a hypothetical future internal caller that invokes that module directly; it is not reachable from any external request today.

## L6 - Node-conflict validation race, in detail

`check_nodes_have_open_tickets()` queries DynamoDB, sees no conflict, and *then* the request is allowed onto the queue - there is a real window between that read and the eventual write where a second, concurrent CREATE for a *different* ticket ID targeting an overlapping node can pass the same check. SQS FIFO ordering doesn't close this gap either: messages are grouped by `MessageGroupId=ticket_id`, so two different ticket IDs are never serialized against each other by the queue, only against themselves.

In this repo, that's an honest limitation, not a solved problem: the actual node-attachment write happens in the downstream ticket-processor Lambda, which isn't included here. The correctness guarantee has to live there, as a conditional write at write time - e.g. a `TransactWriteItems` call that puts a per-node "claim" item with `ConditionExpression: attribute_not_exists(node_id)` (or an equivalent condition on the ticket item itself) as part of the same transaction that creates the ticket, so two concurrent attempts to claim the same node can't both succeed no matter how the pre-queue check answered. Treat the validation layer here as a fast, good-UX early rejection for the common case - not as the system's sole uniqueness guarantee.

## L7 - Fail-closed validation, in detail

If DynamoDB can't be reached at all during a validation lookup, `run_prequeue_validation()` returns a `503 VALIDATION_SERVICE_UNAVAILABLE` and blocks the request, overriding shadow mode. This is a deliberate tradeoff: an earlier version treated a lookup failure as "ticket not found" and let the request through, on the theory that downstream processing would catch any resulting duplicate. That downstream safeguard doesn't exist in this repo (see L6), so silently proceeding on an unverifiable check was judged more dangerous than briefly rejecting new requests during a genuine backend outage. This now applies to *partial* failures too, not just total ones - see "Partial DynamoDB failures were silently treated as fail-open" below.

## L8 - Ticket-uniqueness scan, in detail

Closing the duplicate-ticket gap (see "Duplicate tickets could evade the CREATE existence check" below) meant `check_ticket_exists()` can no longer stop at "no per-node match" when nodes were supplied - it falls through to a parameterized PartiQL `begins_with()` scan by `ticket_id` to rule out the ticket existing under a *different* node set. An earlier version of that scan made a single `execute_statement` call with `Limit=200` and treated an empty result as "doesn't exist" - which is wrong, because DynamoDB's `Limit` bounds items *evaluated per page*, not items *matched*. A table with more than ~200 items ahead of this ticket's rows in scan order could return zero matches on page one even though the ticket genuinely exists further in, producing a false negative on exactly the check this function exists to get right (duplicate CREATE detection, and UPDATE/CLOSE existence checks that use the same fallback).

The fix follows `NextToken` across pages, bounded by `MAX_TICKET_LOOKUP_PAGES` (5 pages, ~1,000 items) so the entry Lambda's 23-second timeout can't be exhausted by an unbounded scan. That narrows the false-negative window from "any table over 200 items" to "any table over ~1,000 items ahead of this ticket in scan order," which is considerably better but is still a bound, not a guarantee - "authoritative," the word an earlier version of this documentation used for this lookup, overstated what it actually does. The real fix, which removes the gap entirely rather than shrinking it, is a Global Secondary Index on `Ticket_Number` (or a dedicated ticket-header item keyed by `ticket_id` alone) so this becomes an indexed point lookup instead of a scan with any page limit at all.

## L9 - OpCo scoping vs. authorization, in detail

Every DynamoDB lookup in `prequeue_validation.py` (`check_ticket_exists()`, `check_nodes_have_open_tickets()`) takes an `opco` parameter and filters on the table's `opco` attribute (lowercase, unlike the other `Pascal_Case_With_Underscores` fields - see `parse_dynamodb_item()`'s docstring), and `entry_handler.py` passes the request body's `OpCo` field through end to end. That closes the functional gap a peer review raised: without it, a ticket ID or node ID reused across two operating companies sharing this table would look like a duplicate or a conflict even though the two OpCos' outages have nothing to do with each other.

What this doesn't do is authenticate that value. `OpCo` is still read straight from the request body and trusted as-is - nothing in this repo checks that the caller is actually authorized to act as the OpCo it claims. Closing that gap requires an authorization layer that derives the caller's permitted OpCo(s) from their authenticated identity (an API-key mapping, a JWT claim, or equivalent) and either overwrites the request's `OpCo` with that authorized value or rejects the request outright when the two disagree, before it ever reaches this validation layer - conceptually, that belongs in the API-key/routing Lambda in front of this repo's entry Lambda, not in the code sampled here.

## L10 - CREATE/UPDATE-CLOSE timing race, in detail

`entry_handler.py` enqueues a CREATE message and returns success as soon as the SQS send succeeds - the actual DynamoDB item is written later, by the downstream processor Lambda (not included in this repo), when it dequeues that message. `validate_update_request()`/`validate_close_request()`, on the other hand, do a synchronous, strongly-consistent `check_ticket_exists()` read at request time. A client that CREATEs a ticket and then immediately UPDATEs or CLOSEs it - a plausible pattern (e.g. a CREATE immediately followed by a correction) - can have that second request's existence check run *before* the processor has finished writing the ticket, producing a `404 TICKET_NOT_FOUND` for a ticket that, from the caller's point of view, was just accepted.

To be precise about what does and doesn't hold here: the shared `LifecycleTicketQueue`'s `MessageGroupId=ticket_id` ordering guarantee ("Separate per-intent queues never actually guaranteed lifecycle ordering," below) is correct and unaffected - the processor genuinely will observe the CREATE message before the UPDATE message. The gap this limitation describes is entirely upstream of the queue: UPDATE/CLOSE's pre-queue validation reads the database directly, not the queue, so queue ordering can't help it. This also meant `tests/README.md` scenario 14's original wording overstated what was fixed - it described "lifecycle ordering across intents" as fully closed, when what was actually closed is *processor-side* ordering once messages are enqueued, not the *pre-queue validation* race described here. That scenario's wording has been corrected, and two new scenarios cover this gap explicitly.

Four ways to close this were weighed:

1. **Make CREATE asynchronous end-to-end** - return `202 Accepted` immediately and require the client to poll or accept a webhook before treating the ticket as real. Correct, but it changes the API's contract (every existing CREATE caller currently gets a synchronous `200` and treats it as "done") and pushes complexity onto every client. Rejected as disproportionate to the problem for a `Devices`-list-sized outage-tracking API.
2. **Write a synchronous reservation record from the entry Lambda itself** - have `entry_handler.py` write a minimal placeholder item (just `Ticket_Number`/`Node_ID`/a `pending_create` status) directly to DynamoDB before enqueueing, so the existence check has something to find immediately, then let the processor overwrite it with the full item. This is the most promising option and is the one sketched below, but it requires coordinating the placeholder item's shape with whatever the downstream processor Lambda expects to read/overwrite - that processor isn't part of this repo, so the exact contract can't be finalized here without guessing at a schema this repo doesn't own.
3. **A separate ingestion-state table** just for "is a CREATE for this ticket_id currently in flight" - avoids touching the main ticket table's schema, but is a second source of truth to keep consistent with the real one, and doesn't help the CREATE-then-CLOSE variant of this same race (CLOSE would need to check the same state table too).
4. **Document it as an expected, retryable eventual-consistency window and make the 404 say so** - the option actually implemented here. `validate_update_request()`/`validate_close_request()`'s `404 TICKET_NOT_FOUND` response now includes a `note` field telling the caller the ticket may still be in flight and to retry shortly, rather than a bare 404 that reads as "this ticket ID is wrong."

Option 4 is what's implemented in this repo; it doesn't close the race, it makes the race's symptom self-explanatory to the caller instead of a confusing false negative. Option 2 is the real fix and is sketched below as a planned addition, explicitly **not implemented in this repo** because it would need to be built against the downstream processor's real (and here, unincluded) read/write contract to avoid two Lambdas racing each other on the same item instead of racing the client:

```python
# Planned fix (NOT implemented in this repo): entry_handler.py writes a
# minimal reservation item synchronously, before enqueueing, so a same-
# instant UPDATE/CLOSE existence check finds *something* rather than
# nothing. The downstream processor Lambda (outside this repo) would need
# to overwrite/complete this item rather than treating a fresh PutItem as
# the only way a ticket comes into existence - that contract has to be
# agreed with that Lambda's real implementation, not assumed here.
dynamodb_client.put_item(
    TableName=TABLE_NAME,
    Item={
        'Node_ID': {'S': node_id},
        'Ticket_Number': {'S': f'{ticket_id}_{node_id}'},
        'Ticket_Status': {'S': 'pending_create'},  # processor overwrites with the real status
        'opco': {'S': opco},
    },
    ConditionExpression='attribute_not_exists(Ticket_Number)',  # don't clobber a real write that beat us here
)
```

## L11 - Dedup/correlation-id mismatch, in detail

`build_dedup_id()` makes `MessageDeduplicationId` a hash of the request's actual content (`ticket_id`, `intent`, `opco`, `category`, sorted nodes) - see "SQS deduplication ID didn't actually deduplicate retries," below, for why that was the right fix for making retries actually dedupe. But `correlation_id` is deliberately *not* part of that hash (a genuine retry can carry a different `correlation_id` than the original attempt, and including it would defeat dedup entirely - two sends of the same business request would get different hashes and never collapse). The consequence: `entry_handler.py` always builds and returns its own fresh `correlation_id` in the synchronous `200` response, regardless of whether the SQS send it just made was accepted as a new message or silently collapsed into an in-flight one within the 5-minute dedup window. When it collapses, only the *original* message's `correlation_id` will ever reach the processor, DB-write, and notification Lambdas - the second caller is holding a `correlation_id` that is valid for its own synchronous response but will never appear in a single downstream log group, breaking the "one correlation_id, one traceable path" property this API otherwise guarantees.

This is a real, unresolved gap, not a hypothetical: SQS's `SendMessage` API doesn't report back whether a given send was deduplicated against an existing message versus accepted as new, so the entry Lambda has no way to detect this at send time even if it wanted to log a warning. Closing it properly needs a different mechanism than content-based FIFO dedup: a caller-supplied idempotency key (or the existing dedup hash used as one) written to a small results-cache table on first receipt, with `entry_handler.py` checking that table before generating a fresh `correlation_id` and returning the *original* request's stored `correlation_id`/response on a repeat within the idempotency window instead of a new one. That's a real architectural addition - a new table, a conditional write, and a cache-hit code path - not implemented here because SQS's dedup behavior was believed (until this finding) to already provide equivalent protection; it provides message-collapse protection, not response-consistency protection, which turned out to be a different guarantee.

```python
# Planned fix (NOT implemented in this repo): an idempotency-result cache
# keyed by the same content hash already used for MessageDeduplicationId,
# so a retry within the window gets back the *original* correlation_id
# instead of a fresh one that will never appear in downstream logs.
dedup_key = build_dedup_id(ticket_id, intent, nodes, opco=opco, category=category)
try:
    dynamodb_client.put_item(
        TableName=IDEMPOTENCY_TABLE,
        Item={
            'dedup_key': {'S': dedup_key},
            'correlation_id': {'S': correlation_id},
            'ttl': {'N': str(int(time.time()) + 300)},  # matches the SQS dedup window
        },
        ConditionExpression='attribute_not_exists(dedup_key)',
    )
except ConditionalCheckFailedException:
    # Someone got here first within the window - hand back their identity,
    # not a fresh one that will never be seen downstream.
    existing = dynamodb_client.get_item(TableName=IDEMPOTENCY_TABLE, Key={'dedup_key': {'S': dedup_key}})
    correlation_id = existing['Item']['correlation_id']['S']
```

## Major resolved issues, in full

**Ticket-lookup false negatives on UPDATE/CLOSE.** An early version queried DynamoDB with an exact string match on ticket ID, which silently failed to match tickets whose IDs picked up incidental leading/trailing whitespace or formatting differences from the upstream system - surfacing as spurious `404 TICKET_NOT_FOUND` errors. The fix switched to a PartiQL `begins_with()` query, which is intentionally more tolerant of that kind of drift. The tolerance for formatting drift here is deliberate, closing a real failure mode, not an unnecessary complication - if you're tempted to "simplify" this back to a plain equality query, don't.

**Over-strict validation on UPDATE/CLOSE.** Validation originally applied the same category/impact rules to every intent. In practice, category and impact fields legitimately change over a ticket's lifetime as the upstream system refines its assessment (e.g. "Loss of service" → "Degraded") - and a CLOSE request would get rejected because the current value no longer matched what CREATE had validated. The fix was to only validate category/impact on CREATE, and let UPDATE/CLOSE trust whatever the upstream system currently reports. This is the origin of the "validate on creation, trust on closure" principle that shows up throughout the codebase.

**PartiQL injection and a response-shape bug in the fallback ticket lookup (security review).** The no-nodes fallback path in `check_ticket_exists()` built its PartiQL statement by interpolating the caller-supplied `ticket_id` directly into the query string, and separately returned raw DynamoDB attribute-value wrappers (e.g. `{"S": "closed"}`) instead of plain values - which meant a `Ticket_Status == 'closed'` comparison downstream could silently fail to match on that path. Both are fixed: the query now uses a parameterized PartiQL statement (`?` placeholder with a `Parameters` list) instead of string interpolation, `ticket_id`/`node_id` values are validated against a strict allowlist pattern before touching any query, and the fallback path reuses `parse_dynamodb_item()` like every other lookup does. If you add a new DynamoDB lookup to this module, run caller-supplied values through `_require_safe_identifier()` first and never f-string them into a PartiQL statement.

**SQS deduplication ID didn't actually deduplicate retries (security review).** The entry Lambda generated `MessageDeduplicationId` from a random UUID on every send. That satisfies SQS FIFO's "must be unique" requirement trivially, but it also means a genuine client retry of the exact same request gets a *different* ID each time - so FIFO's content-dedup protection, which the architecture docs credited with "protecting against a retried CREATE," was never actually engaged. The dedup ID is now a SHA-256 hash of `(ticket_id, intent, sorted nodes)`, so an identical retry within the 5-minute dedup window collapses into one message, while a legitimately different request (e.g. an UPDATE with a changed node list) still gets its own ID.

**Separate per-intent queues never actually guaranteed lifecycle ordering (release review).** CREATE, UPDATE, and CLOSE were each routed to their own FIFO queue, and CLEANUP shared the CLOSE queue. FIFO only orders messages within the *same queue and message group* - it never orders across queues at all - so a fast UPDATE or CLOSE could reach the processor before the CREATE that opened the ticket, directly contradicting the "ordering per ticket ID" guarantee documented elsewhere in this repo. The fix collapses all four lifecycle intents onto a single `LifecycleTicketQueue`, still grouped by `MessageGroupId=ticket_id`, so ordering is now actually enforced by the queue rather than asserted in a comment. The cost is the isolation and independent-scaling benefits a per-intent split gave up - see "Why one shared lifecycle queue instead of one per intent?" in [architecture-overview.md](architecture-overview.md) for that tradeoff.

**Duplicate tickets could evade the CREATE existence check by naming different nodes (release review).** `check_ticket_exists()` only ran its fast, per-node partition-key lookup when the caller supplied a node list, and returned "not found" the moment that lookup came up empty - without ever checking whether a ticket with that exact `ticket_id` existed under a *different* set of nodes. Since node lists drift over a ticket's life (UPDATE replaces them wholesale - see L4) and a duplicate CREATE could simply name nodes the original ticket never touched, ticket-ID uniqueness was never actually being enforced by node overlap alone. The fix makes the ticket-ID-scoped PartiQL scan a second pass whenever the per-node lookup finds nothing, so a duplicate `ticket_id` is caught regardless of which nodes it's submitted with. See L8 for why that scan is a bound, not a guarantee.

**Partial DynamoDB failures were silently treated as fail-open (release review).** Both `check_ticket_exists()` and `check_nodes_have_open_tickets()` only raised `ValidationBackendError` when *every* node lookup in a request failed - if 4 of 5 queries succeeded and found no conflict but the 5th errored, that 5th node's real state was unknown, yet the function returned "no conflict" for it anyway. That's the same fail-open failure mode L7 was written to close, just triggered by a partial rather than total outage. Both functions now raise `ValidationBackendError` the moment *any* node lookup in the batch fails, regardless of how many others succeeded - a request can't be approved on a validation check the system couldn't fully perform.

**A CREATE with no nodes bypassed duplicate/conflict validation entirely (correctness review).** `Devices` is documented as required for CREATE, but nothing enforced that: `run_prequeue_validation()` had a `validate_create_request(ticket_id, nodes) if nodes else {'valid': True}` guard that skipped the whole check - including the ticket-existence lookup - the moment `nodes` was empty. A CREATE with no `Devices` field sailed through as automatically valid. Fixed at both layers: `entry_handler.py` now rejects a nodeless CREATE outright with `400`, and `prequeue_validation.py` no longer has the bypass at all - `validate_create_request()` always runs, and handles an empty node list correctly on its own (falling back to the ticket-ID-scoped lookup rather than skipping validation).

**`OpCo` was documented as required but never checked (correctness review).** The entry Lambda read `body.get('OpCo')` and passed it straight into the SQS message body without ever confirming it was present, despite the API reference listing it as a required field. A request missing `OpCo` was accepted and queued anyway. Fixed: `entry_handler.py` now returns `400 Bad Request` for a missing `OpCo` before validation or enqueueing.

**Malformed node IDs were silently skipped instead of rejected (correctness review).** Both `check_ticket_exists()` and `check_nodes_have_open_tickets()` filtered out any node ID that failed the identifier-format allowlist with a bare `continue`, then validated whatever was left - so a request naming one legitimate node and one malformed one got checked as if the malformed one had simply never been submitted, rather than being told the request itself was invalid. Both functions now call `_require_safe_identifier()` on every node ID and let a mismatch raise `InvalidIdentifierError`, which `run_prequeue_validation()` already turns into a `400` for the caller - the same handling a malformed `ticket_id` already got.

**The SQS deduplication hash omitted fields that distinguish genuinely different requests (correctness review).** `build_dedup_id()` hashed only `(ticket_id, intent, sorted nodes)`. Two different requests that happened to share all three - e.g. the same ticket number reused across two different OpCos, or a CREATE resubmitted moments later with a corrected `category` - would collapse into a single SQS message within the 5-minute FIFO dedup window, silently dropping the second request instead of processing it. `opco` and `category` are now part of the hashed content too.

**`correlation_id` was only ever read from a case-sensitive header, ignoring the documented body field (correctness review).** The API reference lists `correlation_id` as an accepted JSON body field, but the entry Lambda only ever checked `event['headers']['X-Correlation-Id']` with exact casing - a client sending the conventional lowercase `x-correlation-id` header, or supplying the field in the body as documented, got a server-generated correlation ID instead of the one it provided, breaking its ability to correlate its own request against pipeline logs. Fixed: header lookup is now case-insensitive, and a body-supplied `correlation_id` is used when no header is present.

**Cleanup only ever read the first page of stale tickets (correctness review).** `find_stale_tickets()` made a single `execute_statement` call with `Limit=500` and returned whatever came back, ignoring the `NextToken` DynamoDB returns when more matching items exist. On a day with more than 500 stale tickets, everything past the first page was never queued for closure by that run - and since PartiQL scan order isn't guaranteed to track `Ticket_Creation_Date`, a later run's first 500 aren't reliably "the ones missed last time" either, so some stale tickets could go unclosed indefinitely. Fixed: `find_stale_tickets()` now paginates through every page via `NextToken`, bounded by a `MAX_CLEANUP_PAGES` safety cap (10,000 tickets) to protect the Lambda's own timeout on a pathological backlog, logging a warning if that cap is ever hit.

**The ticket-ID-scoped lookup stopped after one page, which could miss a real match (peer review).** As described in L8, `check_ticket_exists()`'s PartiQL fallback made a single `execute_statement` call with `Limit=200` and returned "not found" the moment that call's `Items` came back empty, without ever checking `NextToken`. `Limit` bounds items evaluated per page, not items matched, so a table with enough items ahead of a given ticket's rows in scan order could report a real, existing ticket as not found - a false negative that would let a duplicate CREATE through, or 404 a legitimate UPDATE/CLOSE. Fixed: the lookup now follows `NextToken` up to a `MAX_TICKET_LOOKUP_PAGES` safety cap (5 pages) instead of stopping at page one, logging a warning if the cap is ever hit with more results still available.

**`OpCo` was threaded through the SQS message body and the dedup hash, but never into the DynamoDB queries that decide duplicates and conflicts (peer review).** `check_ticket_exists()` and `check_nodes_have_open_tickets()` matched purely on `ticket_id`/`node_id`, with no `opco` condition anywhere in their `KeyConditionExpression`, `FilterExpression`, or PartiQL `WHERE` clause - so on a table shared across operating companies, a ticket ID or node ID reused by a different OpCo would look like this OpCo's duplicate or conflict. Fixed: both lookup functions, and the `validate_create_request()`/`validate_update_request()`/`validate_close_request()`/`run_prequeue_validation()` chain that calls them, now accept and apply an `opco` filter against the table's `opco` attribute. See L9 for what this fixes and what it deliberately doesn't (caller-to-OpCo authorization).

**Cleanup grouped nodes under a truncated ticket ID for any ticket number containing an underscore (peer review).** `group_nodes_by_ticket()` recovered the ticket ID from each item's `Ticket_Number` sort key (`"{ticket_id}_{node_id}"`) with `Ticket_Number.split('_')[0]` - but `_SAFE_ID_PATTERN` in `prequeue_validation.py` allows underscores in ticket IDs, so a ticket like `INC_2026_001` was silently regrouped and published for closure under ticket ID `INC` instead of `INC_2026_001`. Fixed: the function now strips the exact known `_{node_id}` suffix (using the `Node_ID` already present on the same item) instead of splitting on the first underscore, and skips (with a logged warning) any item whose `Ticket_Number` doesn't end with that expected suffix rather than guessing.

**The operations dashboard queried a log group name that didn't match what the included CloudFormation actually creates (peer review).** `EntryValidationLogGroup` in the CFN template is named `/aws/lambda/outage-entry-validation-${Environment}` (e.g. `-prod`), but `dashboards/operations-dashboard.json`'s three log-based widgets queried the bare `/aws/lambda/outage-entry-validation`, with no environment suffix - a dashboard imported as-is against a stack deployed from this repo's own CFN template would query a log group that doesn't exist and show no data. Fixed: the dashboard's queries now match the `prod` environment's actual log group name (`Environment`'s CFN default); swap the `-prod` suffix for `-dev` when importing against a dev deployment.

**A CloudFormation `Region` input parameter could disagree with the region the stack actually deployed into (peer review).** The IAM policies' DynamoDB table ARNs were built with `!Sub 'arn:aws:dynamodb:${Region}:${AWS::AccountId}:table/...'`, where `Region` was a manually supplied template parameter (default `us-east-1`) rather than the `AWS::Region` pseudo parameter. Deploying the same template into a different region without also updating that parameter would produce IAM policies granting access to a table ARN in the *wrong* region while every resource the template actually creates lands in the *right* one - a silent access failure at runtime rather than a deploy-time error. Fixed: both ARNs now use `${AWS::Region}`, which is always correct for the stack's actual deployment region and removes one more manually-supplied value that could drift, and the `Region` parameter was removed as no longer needed.

**The non-TLS-transport deny policy only covered the main lifecycle queue, not either dead-letter queue (peer review).** `PipelineQueuePolicy` denied any `sqs:*` action over a non-TLS connection on `LifecycleTicketQueue`, but `PipelineDeadLetterQueue` (which receives redriven copies of the same ticket messages after repeated processing failures) and `SchedulerDeadLetterQueue` had no equivalent policy - there's no principled reason a DLQ holding the same class of data, or feeding the same operational response, should be held to a lower transport-security bar than the queue it's attached to. Fixed: added `PipelineDeadLetterQueuePolicy` and `SchedulerDeadLetterQueuePolicy`, identical in shape to the existing one, scoped to their respective queues.
